# Accessibility

Source of truth for accessibility rules in this repo. **Target: WCAG 2.2 AAA where feasible; AA is the non-negotiable floor.** Anything that ships UI — new components, route changes, schema-driven blocks — has to satisfy the checklist at the bottom of this doc before it merges.

Scope: the Next.js frontend (`frontend/`). The Sanity Studio is out of scope here — it inherits Sanity's own a11y posture.

---

## Color & contrast

Tokens live in `frontend/app/globals.css` (`:root`, mapped into Tailwind v4 via `@theme inline`). The site is **light only** (D14). The measured contrast table for every token pair is in the build plan (§7.2); the key ones:

- `--foreground` on `--background` — 15.66:1. AAA.
- `--muted-foreground` on `--background` — 7.64:1 (7.00:1 on `--muted`). AAA body.
- `--primary-foreground` on `--primary` — 11.40:1. AAA.
- `--brand-accent` (sunflower) is 1.62:1 on paper: **fills on dark/primary surfaces only**, never text or meaningful UI on a light background. Use `--brand-accent-strong` (3.58:1, UI-pass) for rules, underlines and flourishes a sighted user must perceive.
- `--border` (1.28:1) is decorative only; control boundaries use `--input` (3.49:1).

Rules:

- **Never introduce a new text token without measuring its contrast.** Use a calculator (WebAIM, Stark, or the formula in WCAG 2.x §1.4.3) — eyeballing it is not acceptable. Add the pair to the §7.2 table.
- Body text (`prose`, card content, captions, footer subtext) must be ≥ 7:1.
- Large text (≥ 18pt regular or ≥ 14pt bold) and incidental UI text may sit at AA (≥ 4.5:1) when AAA breaks visual hierarchy — but you must justify it in the PR.
- Non-text contrast (focus rings, borders that carry meaning, icon-only buttons) must be ≥ 3:1.
- Don't hardcode hex colors in components. Reach for the token (`text-foreground`, `text-muted-foreground`, `bg-muted`, `border-border`, `bg-destructive`, etc.). Hex sneaks past contrast review.
- Text over photography (the masthead) relies on the scrim tiers in `Masthead.tsx`; re-check them whenever a masthead image changes.

## Keyboard, focus, motion

- shadcn's `focus-visible:ring-1 focus-visible:ring-ring` is the standard. Don't override it on `Button`, `CollapsibleTrigger`, `SheetTrigger`, etc. If you compose a non-button element into a clickable target (the gallery's overlay tile `<button>` is the canonical example), copy the same `focus-visible:outline-none focus-visible:ring-1 focus-visible:ring-ring` so keyboard focus stays visible.
- Tab order follows DOM order. Don't use `tabIndex={1+}` to force ordering — restructure the DOM instead. `tabIndex={-1}` is fine for elements that should be focusable programmatically but not via tab.
- Radix primitives (`Collapsible`, `Sheet`/Dialog) handle keyboard and roving focus correctly out of the box. Don't wrap them in custom `onKeyDown` handlers that can intercept escape, arrow keys, or `Tab`.
- Respect `prefers-reduced-motion`. `tw-animate-css` honors it automatically for the `animate-*` and `fade-*` utility families — don't add hand-rolled `transition`/`@keyframes` that ignore it.
- Don't trap focus outside a true modal context. `Sheet` (Radix Dialog) traps correctly; reproducing this manually is almost always wrong.

## Semantics & ARIA

- **Heroicons inside buttons** that already have visible text or an explicit `aria-label`: the icon component is decorative — make sure it carries `aria-hidden="true"`. Heroicons in `@heroicons/react/24/outline` already do; custom SVGs (e.g. `SocialIcon`) must add it explicitly.
- **Icon-only buttons** (mobile menu trigger, back-to-top, lightbox arrows/close, PortableText heading-anchor): one of `aria-label` or a `<span class="sr-only">` is required. `aria-label` wins when both are present, but doubling up is harmless and helps a few legacy AT combos. Don't ship an icon-only control without one of these.
- **Full-card links** (program cards and any future card grid): the link must carry `aria-label={title}` so the empty-link-text SR announcement ("link") doesn't surface. The visible card title is read separately as a heading by SRs, which is fine — duplication is preferable to silence.
- **External links** (`target="_blank"`): always pair with `rel="noopener noreferrer"` and ensure the link text or `aria-label` makes the destination obvious ("Facebook", not "click here"). If the icon implies "opens in a new tab" you may want to surface that in the `aria-label` for SR users.
- **Pull quotes** (`pullQuote` block) are `<figure><blockquote>` + `<figcaption>`. When a quote repeats the page's own copy, editors tick `repeatsText` and the figure is `aria-hidden` so it isn't read twice; an original quotation must stay exposed.
- **Headings** are a single H1 per route. Page builder blocks render H2/H3; never re-introduce an H1 inside `CallToAction` / `InfoSection`. The prose typography plugin already styles them.
- **Landmarks**: the rail's `<nav>`, `<main>` and `<footer>` are present in the root layout — keep them. New route layouts must preserve a single `<main>`.
- **Forms** (none — D6, contact is `mailto:`/`tel:`; relevant if that ever changes): every input needs a programmatically associated `<label>` (via `htmlFor`/`id` or wrap), not just placeholder text. Use shadcn's `Label` + `Input` when those are added.
- **Live regions**: toasts use shadcn's `sonner` wrapper which sets `aria-live="polite"`. Don't re-announce the same status from an additional region.

## Images

- `next/image` and `SanityImage` (built on `sanity-image`) both require `alt`. **Decorative** images get `alt=""` — never omit the prop.
- Sanity authors author alt text on assets via `@sanity/assist` AI suggestions; rely on `image.asset->altText` first, fall back to `image.alt`, then to a sensible decorative `""`. Never invent alt text in the component layer.
- LCP images (the masthead on `/`, `/[slug]` and `/programs/[slug]`) should set `priority` on `next/image` (or the equivalent on `SanityImage`) so they're preloaded.

## Gallery & embedded video

The `gallery` page-builder block (grid / masonry / carousel + optional lightbox + YouTube/Vimeo video):

- **Video captions (WCAG 1.2.2, Level A).** `galleryVideo` embeds an external YouTube/Vimeo player, so captions live on the **source** video — there is no way to add them in this app. **Authors must enable captions on the YouTube/Vimeo source.** The schema's `title` is required and is used as both the facade button's `aria-label` and the `<iframe title>`.
- **Lazy facade.** A video tile is a labelled `<button>` over a poster; the third-party `<iframe>` (and its JS) loads only on click — no autoplaying media on load (1.4.2), lower JS/TTI.
- **Lightbox** is a Radix `Dialog`: focus-trap, Esc-to-close, `aria-modal`, labelled by an `sr-only` `DialogTitle` and described by a `DialogDescription`. The `n / total` counter is an `aria-live="polite"` region; arrows/close are icon buttons with `aria-label`; the Embla region exposes `role="region"` + per-slide `aria-label`s.
- **No carousel autoplay.** Auto-advancing content requires a visible pause control (2.2.2); the carousel is fully operable via arrows / dots / swipe / keyboard, so autoplay is intentionally not wired.
- **Tiles are buttons.** With the lightbox on, each tile is a transparent overlay `<button>` (`aria-label` "View image: …" / "Play video: …") carrying the standard `focus-visible:ring-1 focus-visible:ring-ring`. Decorative scrims and the play badge are `aria-hidden`.
- **Target size.** Nav arrows and the lightbox close are ≥ 44×44 px (AAA, 2.5.5); carousel dots use a 24 px hit area around an 8 px visual (AA, 2.5.8).
- **No CLS.** Every tile box has a defined aspect ratio (utility class, or the asset's intrinsic `aspectRatio` from `metadata`), so nothing reflows as media loads.
- **Masonry reading order.** CSS multi-column reorders items visually (top→bottom per column); DOM / tab / SR order stays source order. Use the grid layout when strict left-to-right order matters.

## Navigation

CMS-driven side navigation (`SideNav` → `SideNavLinks`, shared by the desktop rail and the mobile drawer `SideNavMobile`). The schema models two item types: `navLink` (a leaf, reusing the `link` object) and `navDropdown` (a labelled group whose `title` is **not** a link — e.g. Programs).

- **Group triggers are buttons that never navigate.** `navDropdown` renders a Radix `CollapsibleTrigger` (a real `<button>` with `aria-expanded`). Only its child `navLink`s navigate.
- **Closed groups are unmounted**, not force-mounted and hidden — force-mounting put hidden links in the tab order.
- **Active leaf gets `aria-current="page"`**, computed by matching the resolved href against `usePathname()`; the active styling keys off `aria-[current=page]:…`. **External links are never marked active.** Externality is decided by the resolved href (anything starting with `/` is internal), not by `linkType` — see `navHelpers.ts`.
- **Hamburger is an icon-only `<button>` whose label reflects state** (`aria-label={open ? 'Close menu' : 'Open menu'}` + `aria-expanded`); the bars are `aria-hidden`.
- **External links** (`link.openInNewTab`): `ResolvedLink` emits `target="_blank"` + `rel="noopener noreferrer"`; the leaf adds a visible `ArrowTopRightOnSquareIcon` (decorative) **and** an `sr-only` "(opens in new tab)" cue.
- **The mobile menu is a full-screen, non-modal Radix Sheet that drops from under the top bar.** The bar stays visible and live (its hamburger morphs into the close X), which a modal Sheet can't allow — so the modal contract is restored with platform primitives, not a hand-rolled trap: `inert` on everything outside the bar + panel (focus containment, page hidden from AT), `overflow: hidden` on `<html>` (scroll lock). Radix still owns Esc, focus into the panel, and focus back to the hamburger. Interactions inside the bar don't dismiss (`onInteractOutside`); crossing to `lg` with the menu open closes it so the page never stays inert. Links close the menu via `onNavigate` so focus doesn't strand on an unmounted node.
- **Active leaf is a solid `--primary` pill** (white on academy blue ≈ 10:1). The sunflower is not used for nav state.
- **Rail and ContactHub targets are ≥ 44px** (AAA 2.5.5).
- **Single H1 preserved.** Nav introduces no `<h1>`; the drawer's `SheetTitle` is the Dialog's accessible name, not a page heading.
- **Motion is gated.** The ContactHub entrance lives under `@media (prefers-reduced-motion: no-preference)` in `globals.css`; Collapsible height rides `tw-animate-css`; the menu's drop-down carries explicit `motion-reduce:…animate-none`; the hamburger morph and chevron rotation use `motion-reduce:transition-none`.

## Performance for a11y

CLS and TTI are a11y issues — they break SR pacing and motor-impaired user interaction. Honor the existing posture:

- RSC by default. Only opt into `'use client'` for hooks or Visual Editing primitives.
- Draft-mode `<Suspense>` fallbacks must match the footprint of what streams in (the masthead-sized `Skeleton` on `/` and `/[slug]`). Mismatched skeletons reintroduce CLS.
- No layout-shifting fonts. `next/font` is wired for Inter (body) + Outfit (headings) in `app/layout.tsx`; don't add a third runtime-loaded font.
- Lighthouse target: ≥95 Accessibility *and* ≥90 Performance on every route (plan S12). Run before shipping any visual change.

## Tooling & skills

When making non-trivial UI changes, run the `design:accessibility-review` skill against the changed page or component. Treat its findings as authoritative for WCAG 2.1 AA; AAA gaps it surfaces are addressed when feasible per the rules above. Skill location: `design:accessibility-review` (installed plugin).

Local manual checks before opening a PR:

- Tab through the changed page top to bottom — every interactive control receives a visible focus ring, no traps, no skipped controls.
- Check focus on dark surfaces too (brand CTA, masthead, brand panels) — the ring must stay visible there.
- VoiceOver (macOS) / NVDA (Windows) sweep — each interactive control has a meaningful accessible name; no empty "link" or "button" announcements.
- Zoom to 200% in the browser — no horizontal scrolling, no clipped text.
- Lighthouse Accessibility audit on the affected route(s).

For schema-driven blocks (`pageBuilder`), validate that every author-controlled string that could end up unlabeled (e.g. CTA button text, image alt) has a Studio-side validation rule. A blank `button.text` shouldn't be possible to publish.

## Checklist (apply to every UI PR)

- [ ] All new color pairings measured; ≥ 7:1 for body, ≥ 4.5:1 for large/incidental, ≥ 3:1 for non-text. Justification noted in the PR if AA-only.
- [ ] No hardcoded hex colors; all colors come from `globals.css` tokens.
- [ ] Every icon-only button has `aria-label` (or `sr-only` text).
- [ ] Every decorative SVG/icon has `aria-hidden="true"`.
- [ ] Every interactive element is reachable and visible under keyboard focus, including on dark surfaces.
- [ ] Radix primitives used as-is; no custom keyboard handlers wrapping them.
- [ ] Images have explicit `alt` (empty string for decorative).
- [ ] Suspense fallbacks are size-matched to their content.
- [ ] `design:accessibility-review` skill run on the affected route/component.
- [ ] Lighthouse Accessibility ≥ 95 on the affected route.
- [ ] Nav: disclosure triggers are buttons (never links), expose open state, and don't navigate; active leaf carries `aria-current="page"`; closed groups are unmounted. (See Navigation above.)

If a rule has to be broken, document the reason in the PR body and link the relevant WCAG SC.
