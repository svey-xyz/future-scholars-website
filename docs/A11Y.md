# Accessibility

Source of truth for accessibility rules in this repo. **Target: WCAG 2.2 AAA where feasible; AA is the non-negotiable floor.** Anything that ships UI — new components, route changes, schema-driven blocks — has to satisfy the checklist at the bottom of this doc before it merges.

Scope: the Next.js frontend (`frontend/`). The Sanity Studio is out of scope here — it inherits Sanity's own a11y posture.

---

## Color & contrast

Tokens live in `frontend/app/globals.css` (`:root` for light, `.dark` for dark, mapped into Tailwind v4 via `@theme inline`). Measured ratios for the two body-text pairings:

- Light: `--foreground` (HSL `0 0% 3.9%`) on `--background` (HSL `0 0% 100%`) — ~20:1. AAA.
- Dark: `--foreground` (HSL `0 0% 98%`) on `--background` (HSL `0 0% 3.9%`) — ~19:1. AAA.
- Light: `--muted-foreground` (HSL `0 0% 34%`) on `--background` — ~7.3:1. AAA body. The value was lowered from shadcn's default `45.1%` in Phase 6 (see [SHADCN.md](./SHADCN.md)) because the default failed AAA at 4.74:1.
- Dark: `--muted-foreground` (HSL `0 0% 63.9%`) on `--background` — ~7.8:1. AAA body. Untouched.

Rules:

- **Never introduce a new text token without measuring contrast in both light and dark.** Use a calculator (WebAIM, Stark, or the formula in WCAG 2.x §1.4.3) — eyeballing it is not acceptable.
- Body text (`prose`, `Card` content, post excerpts, dates, captions, footer subtext) must be ≥ 7:1.
- Large text (≥ 18pt regular or ≥ 14pt bold) and incidental UI text may sit at AA (≥ 4.5:1) when AAA breaks visual hierarchy — but you must justify it in the PR.
- Non-text contrast (focus rings, borders that carry meaning, icon-only buttons) must be ≥ 3:1 in both themes.
- Don't hardcode hex colors in components. Reach for the token (`text-foreground`, `text-muted-foreground`, `bg-muted`, `border-border`, `bg-destructive`, etc.). Hex sneaks past contrast review.
- The brand `#f50` accent is intentionally not in the palette right now (see SHADCN.md Decisions). If it returns, re-measure every pair that uses it.

## Keyboard, focus, motion

- shadcn's `focus-visible:ring-1 focus-visible:ring-ring` is the standard. Don't override it on `Button`, `DropdownMenuItem`, `NavigationMenuLink`, `SheetTrigger`, etc. If you compose a non-button element into a clickable target (the absolute `<span>` overlay in `Posts.tsx` is the canonical example), copy the same `focus-visible:outline-none focus-visible:ring-1 focus-visible:ring-ring` so keyboard focus stays visible.
- Tab order follows DOM order. Don't use `tabIndex={1+}` to force ordering — restructure the DOM instead. `tabIndex={-1}` is fine for elements that should be focusable programmatically but not via tab.
- Radix primitives (`NavigationMenu`, `DropdownMenu`, `Sheet`/Dialog, `Tooltip`) handle keyboard and roving focus correctly out of the box. Don't wrap them in custom `onKeyDown` handlers that can intercept escape, arrow keys, or `Tab`.
- Respect `prefers-reduced-motion`. `tw-animate-css` honors it automatically for the `animate-*` and `fade-*` utility families — don't add hand-rolled `transition`/`@keyframes` that ignore it.
- Don't trap focus outside a true modal context. `Sheet` (Radix Dialog) traps correctly; reproducing this manually is almost always wrong.

## Semantics & ARIA

- **Heroicons inside buttons** that already have visible text or an explicit `aria-label`: the icon component is decorative — make sure it carries `aria-hidden="true"`. Heroicons in `@heroicons/react/24/outline` already do; custom SVGs (e.g. `GithubIcon`) must add it explicitly.
- **Icon-only buttons** (mobile menu trigger, ModeToggle trigger, copy-snippet button, PortableText heading-anchor): one of `aria-label` or a `<span class="sr-only">` is required. `aria-label` wins when both are present, but doubling up is harmless and helps a few legacy AT combos. Don't ship an icon-only control without one of these.
- **Full-card links** in `Posts.tsx` and any future card grid: the link must carry `aria-label={title}` so the empty-link-text SR announcement ("link") doesn't surface. The visible card title is read separately as a heading by SRs, which is fine — duplication is preferable to silence.
- **External links** (`target="_blank"`): always pair with `rel="noopener noreferrer"` and ensure the link text or `aria-label` makes the destination obvious ("View on GitHub", not "click here"). If the icon implies "opens in a new tab" you may want to surface that in the `aria-label` for SR users.
- **Headings** are a single H1 per route. Page builder blocks render H2/H3; never re-introduce an H1 inside `CallToAction` / `InfoSection`. The prose typography plugin already styles them.
- **Landmarks**: `<header>`, `<main>`, `<footer>` are present in the root layout — keep them. New route layouts must preserve a single `<main>`.
- **Forms** (none today; relevant when added): every input needs a programmatically associated `<label>` (via `htmlFor`/`id` or wrap), not just placeholder text. Use shadcn's `Label` + `Input` when those are added.
- **Live regions**: toasts use shadcn's `sonner` wrapper which sets `aria-live="polite"`. Don't re-announce the same status from an additional region.

## Images

- `next/image` and `SanityImage` (built on `sanity-image`) both require `alt`. **Decorative** images get `alt=""` — never omit the prop.
- Sanity authors author alt text on assets via `@sanity/assist` AI suggestions; rely on `image.asset->altText` first, fall back to `image.alt`, then to a sensible decorative `""`. Never invent alt text in the component layer.
- LCP images on `/`, `/[slug]`, and `/posts/[slug]` should set `priority` on `next/image` (or the equivalent on `SanityImage`) so they're preloaded.

## Gallery & embedded video

The `gallery` page-builder block (grid / masonry / carousel + optional lightbox + YouTube/Vimeo video):

- **Video captions (WCAG 1.2.2, Level A).** `galleryVideo` embeds an external YouTube/Vimeo player, so captions live on the **source** video — there is no way to add them in this app. **Authors must enable captions on the YouTube/Vimeo source.** The schema's `title` is required and is used as both the facade button's `aria-label` and the `<iframe title>`.
- **Lazy facade.** A video tile is a labelled `<button>` over a poster; the third-party `<iframe>` (and its JS) loads only on click — no autoplaying media on load (1.4.2), lower JS/TTI.
- **Lightbox** is a Radix `Dialog`: focus-trap, Esc-to-close, `aria-modal`, labelled by an `sr-only` `DialogTitle` and described by a `DialogDescription`. The `n / total` counter is an `aria-live="polite"` region; arrows/close are icon buttons with `aria-label`; the Embla region exposes `role="region"` + per-slide `aria-label`s.
- **No carousel autoplay.** Auto-advancing content requires a visible pause control (2.2.2); the carousel is fully operable via arrows / dots / swipe / keyboard, so autoplay is intentionally not wired.
- **Tiles are buttons.** With the lightbox on, each tile is a transparent overlay `<button>` (`aria-label` "View image: …" / "Play video: …") carrying the standard `focus-visible:ring-1 focus-visible:ring-ring`. Decorative scrims and the play badge are `aria-hidden`.
- **Target size.** Nav arrows and the lightbox close are ≥ 44×44 px (AAA, 2.5.5); carousel dots use a 24 px hit area around an 8 px visual (AA, 2.5.8).
- **No CLS.** Every tile box has a defined aspect ratio (utility class, or the asset's intrinsic `aspectRatio` from `metadata`), so nothing reflows as media loads.
- **Masonry reading order.** CSS multi-column reorders items visually (top→bottom per column); DOM / tab / SR order stays source order. Use the grid layout when strict left-to-right order matters.

## Performance for a11y

CLS and TTI are a11y issues — they break SR pacing and motor-impaired user interaction. Honor the existing posture:

- RSC by default. Only opt into `'use client'` for hooks or Visual Editing primitives.
- Stream long lists via `<Suspense>` with a `Skeleton` fallback whose footprint matches the final card (~`h-40 w-full rounded-xl` for `Posts`). Mismatched skeletons reintroduce CLS.
- No layout-shifting fonts. `next/font` is wired for Inter + IBM Plex Mono in `app/layout.tsx`; don't add a third runtime-loaded font.
- Lighthouse target: ≥95 Accessibility *and* ≥95 Performance on `/` in both light and dark. Run before shipping any visual change.

## Tooling & skills

When making non-trivial UI changes, run the `design:accessibility-review` skill against the changed page or component. Treat its findings as authoritative for WCAG 2.1 AA; AAA gaps it surfaces are addressed when feasible per the rules above. Skill location: `design:accessibility-review` (installed plugin).

Local manual checks before opening a PR:

- Tab through the changed page top to bottom — every interactive control receives a visible focus ring, no traps, no skipped controls.
- Toggle light/dark via the `ModeToggle` and re-tab — focus visibility must survive in both themes.
- VoiceOver (macOS) / NVDA (Windows) sweep — each interactive control has a meaningful accessible name; no empty "link" or "button" announcements.
- Zoom to 200% in the browser — no horizontal scrolling, no clipped text.
- Lighthouse Accessibility audit on the affected route(s).

For schema-driven blocks (`pageBuilder`), validate that every author-controlled string that could end up unlabeled (e.g. CTA button text, image alt) has a Studio-side validation rule. A blank `button.text` shouldn't be possible to publish.

## Checklist (apply to every UI PR)

- [ ] All new color pairings measured; ≥ 7:1 for body, ≥ 4.5:1 for large/incidental, ≥ 3:1 for non-text. Justification noted in the PR if AA-only.
- [ ] No hardcoded hex colors; all colors come from `globals.css` tokens.
- [ ] Every icon-only button has `aria-label` (or `sr-only` text).
- [ ] Every decorative SVG/icon has `aria-hidden="true"`.
- [ ] Every interactive element is reachable and visible under keyboard focus in both themes.
- [ ] Radix primitives used as-is; no custom keyboard handlers wrapping them.
- [ ] Images have explicit `alt` (empty string for decorative).
- [ ] Streaming lists have `<Suspense>` + size-matched `Skeleton`.
- [ ] `design:accessibility-review` skill run on the affected route/component.
- [ ] Lighthouse Accessibility ≥ 95 on the affected route in light *and* dark.

If a rule has to be broken, document the reason in the PR body and link the relevant WCAG SC.
